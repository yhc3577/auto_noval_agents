# 研究文档：AI长篇小说自动生成系统

**日期**: 2026-05-10
**功能**: 001-ai-novel-system

## 1. LangGraph 多智能体编排

**决策**: 使用 LangGraph 作为6智能体编排框架

**理由**:
- LangGraph 原生支持状态机、分支、循环，适合6Agent闭环流程
- 与 LangChain 生态无缝集成，可直接使用 LLM 调用链
- 内置 checkpoint 机制，支持断点续跑
- 支持条件路由，满足审核不通过回流重写的分支逻辑

**备选方案**:
- AutoGen：偏对话式多智能体，不适合严格顺序的流水线
- CrewAI：角色定义灵活，但状态管理和循环控制能力较弱
- 自研状态机：完全可控但开发成本高，需自行处理checkpoint和持久化

## 2. 状态持久化与断点续跑

**决策**: Redis 存储 LangGraph State 快照 + MongoDB 持久化全量数据

**理由**:
- Redis 读写速度快，适合存储热状态和进度信息
- MongoDB 持久化章节内容、大纲、审核记录等结构化数据
- LangGraph 内置 RedisSaver/SqliteSaver checkpoint，可直接对接 Redis
- 双层存储确保：Redis 宕机可从 MongoDB 恢复，服务重启可从 Redis 断点续跑

**备选方案**:
- 纯 SQLite：轻量但不适合并发场景和分布式部署
- 纯 MongoDB：持久化可靠但读写延迟高于 Redis
- PostgreSQL：功能强大但对文档型数据（小说内容）不如 MongoDB 灵活

## 3. FAISS 向量记忆方案

**决策**: 使用 FAISS 本地向量库，双向量库隔离设计

**理由**:
- 无需部署额外向量服务，运维成本低
- 每本小说独立索引（私有记忆库），互不干扰
- 全局公共版权比对库共享，跨项目查重
- 本地运行，数据不外泄，商用安全

**备选方案**:
- Milvus：功能强大但需独立部署，运维成本高
- Weaviate：支持混合搜索但资源消耗较大
- Pinecone：云服务，有数据外泄风险和API费用
- ChromaDB：轻量但性能和稳定性不如 FAISS

## 4. Embedding 模型选型

**决策**: 使用 text2vec-base-chinese 或 m3e-base 作为本地 Embedding 模型

**理由**:
- 中文场景下效果优秀
- 模型体积小（~400MB），可本地部署
- 推理速度快，适合实时向量化
- 与 FAISS 配合良好

**备选方案**:
- OpenAI text-embedding-ada-002：效果好但有API费用和数据外泄风险
- BGE-large-zh：效果更好但模型体积大，推理慢
- Cohere：多语言效果好但依赖外部服务

## 5. 大模型选型策略

**决策**: 支持多模型配置，默认使用 Claude 或 GPT-4 级别模型

**理由**:
- 长篇小说创作对模型能力要求高，需要强推理和长上下文
- 通过 LangChain 统一接口，可灵活切换模型
- 配置化管理，用户可按需选择模型和API Key
- 不同Agent可使用不同模型（如审核用轻量模型，写作用强模型）

**备选方案**:
- 固定单一模型：简单但灵活性差
- 全部使用开源模型：成本低但质量可能不足
- 全部使用商业API：质量高但成本高

## 6. 前端实时进度方案

**决策**: 使用 SSE（Server-Sent Events）推送创作进度

**理由**:
- 创作进度是单向推送，SSE 比 WebSocket 更轻量
- FastAPI 原生支持 SSE 响应
- 前端 EventSource API 简单易用
- 自动重连机制，网络中断可恢复

**备选方案**:
- WebSocket：双向通信，但本场景只需单向推送
- 轮询：实现简单但实时性差、浪费资源
- gRPC 流：性能好但前端集成复杂

## 7. 并发控制与分布式锁

**决策**: 使用 Redis 分布式锁控制同一项目的并发创作

**理由**:
- Redis SETNX 原语天然支持分布式锁
- 已有 Redis 实例，无需额外依赖
- 支持锁超时自动释放，防止死锁
- 可扩展到多实例部署场景

**备选方案**:
- 数据库锁：实现简单但性能差
- 进程内锁：仅限单实例，无法扩展
- Zookeeper：功能强大但引入额外依赖过重

## 8. 用户认证方案

**决策**: JWT Token + bcrypt 密码哈希

**理由**:
- JWT 无状态，适合前后端分离架构
- bcrypt 哈希存储密码，安全性高
- Token 可设置过期时间，支持刷新机制
- 实现简单，无需外部依赖

**备选方案**:
- Session + Cookie：有状态，需服务端存储
- OAuth2：适合第三方登录，但本系统为独立部署
- API Key：适合服务间通信，不适合用户登录场景
